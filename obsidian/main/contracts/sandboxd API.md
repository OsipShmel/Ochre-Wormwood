### Общие правила API

Все входящие запросы выполняются в контексте текущего Agent instance.

Ожидается, что `SandboxD` автоматически знает(условно):
- `sandbox_id`;
- `agent_id`;
-  полный контекст текущей `check_session`, если она существует(под контекстом имеется ввиду, какая сессия открыта, на какую уязвимость нацелена; Все логи, относящиеся к данной чек-сессии ассоциированы с ней).
- целевой `vulnerability`, если она установлена для текущей check-session.

Поэтому эти поля не должны передаваться пентест-системой в каждый запрос без необходимости.
Все идентификаторы передаются как strings.

# SandboxD — Pentest Agent API

## ==0. Минимальный API==

В рамках первой реализации я ожидаю, что хватит такого набора методов:

```text
start_check_session()
get_check_session()

change_active_vulnerability() (maybe)

submit_check_result()
finish_check_session()

get_vulnerabilities()     # optional

log()
```

## 1. Назначение

API предназначен для минимального взаимодействия Pentest System с `sandboxd`.

Основные функции:
- открытие и завершение check-session;
- получение доступных для проверки VLS;
- валидируемая фиксация результата проверки;
- передача агентских логов, включая регистрацию событий работы  пентест-системы, инструментов и тп.

API **не предназначен для управления контейнерами, sandbox, сетью или другими системными ресурсами**.

Предполагается, что все необходимые для работы агента статические данные передаются на этапе инициализации sandbox. API используется преимущественно для событий и результатов, возникающих во время работы.

---

# 2. Logging Context Type

Каждое агентское событие относится к одному из logging context.
На текущем этапе определены три типа:

```text
global
check
permanent
```

### `global`

События, относящиеся ко всему Agent instance/Пентет системе и не принадлежащие конкретной check-session.

Примеры:

- запуск/остановка агента;
    
- обновление глобального контекста;
    
- системные ошибки;
    
- события вне check-session;
    
- действия, явно помеченные агентом как глобальные.
    

### `check`

События конкретной check-session.

Контекст однозначно определяется `sandboxd` по активной session.

Примеры:

- reasoning;
    
- tool calls;
    
- tool responses;
    
- target responses;
    
- ошибки во время проверки;
    
- промежуточные действия агента.
    

Физически такие записи могут храниться, например, как:

```text
check_session_<uuid>
```

### `permanent`

Данные, которые должны сохраняться между check-session.

Предназначены прежде всего для потенциального self-improvement / persistent skill state.

Сейчас механизм их хранения не детализируется.

---

# 3. Определение logging context

`sandboxd` самостоятельно определяет context там, где это возможно.

Если активной check-session нет:

```text
log(...) → global
```

Если активна:

```text
session = <uuid>

log(...) → check:<uuid>
```

Агент не передаёт `session_id` в каждом сообщении.

Для события, которое происходит внутри check-session, но относится к глобальному состоянию Agent instance, агент может явно указать:

```json
{
  "context": "global"
}
```

Таким образом, `context` является исключением, а не обязательным параметром.

# 5. VLS API

## 5.1. `get_vulnerabilities`

Возвращает доступные агенту VLS.

### Request

```json
{}
```

### Response

```json
{
  "vulnerabilities": [
    {
      "vulnerability_id": "uuid",
      "title": "SQL Injection in auth component",
      "status": "unchecked",
      "verdict": null,
      "confirmed_by": null,
      "sast": {}
    }
  ]
}
```

Метод является **опциональным для MVP**.

Предполагается, что массив VLS может быть передан агенту заранее при инициализации sandbox. В таком случае агент не требует дополнительного запроса.

`sandboxd` не обязан передавать агенту полный объём внутреннего VLS, если конкретному агентскому runtime достаточно ограниченного представления.

Получает от агента флаг, для проверки его подлинности. Возвращает true/false. 

==**Имеет возможный сайд-эффект:**== после закрепления флага в качестве доказательства уязвимости супервайзер ресетает таргет. 

### Request

```json
{
  "flag": "flag-value"
}
```

### Response
``` json
{
  "valid": true
}
```

Метод не изменяет состояние VLS напрямую.

# 7. `submit_check_result`

Фиксирует результат проверки текущей VLS.

==Агент не может изменять поля VLS напрямую.==

==**Имеет возможный сайд-эффект:**== при принятии системой вердикта VLS получает статус checked и далее доступ к нему может быть ограничен.

### Request

```json
{
  "vulnerability_id": "uuid", // будет указываться только если внутри чек-сессии возможна работа с несколькими уязвимостими

  "verdict": "confirmed",

  "report": {
    "action_taken": "SQL injection attempted against /api/auth",
    "result_details": "Database interaction successfully achieved."
  },

  "proof": {
    "type": "none",
    "details": "..."
  }
}
```

### `verdict`

Допустимые значения:

```text
confirmed
unconfirmed
```

`confirmed` означает, что агент получил достаточное доказательство эксплуатации.

`unconfirmed` означает, что в рамках выполненной проверки уязвимость не была подтверждена.

### `report`

Человекочитаемый результат проверки.

### `proof`

Структурированное описание доказательства.

На текущем этапе предполагаются типы:

```text
flag – в данном кейсе предоставлять флаг не нужно – его необходимо сверить у системы методом check_secret_flag, а далее указать данный маркер как источник док-ва. Супервайзер сам проверит, был ли ранее дескридитирован к-й либо флаг и соотнесет с уязвимостью.

none – строится на заверениях агента, мб этот флаг будет только вреден хз
```

Окончательный enum может быть уточнён позднее.

# 8. Обработка `submit_check_result`

`sandboxd` валидирует:

1. существование `vulnerability_id`; (если таковой используется)
2. наличие активной check-session;
3. соответствие vulnerability текущей session;
4. допустимость текущего состояния VLS;
5. структуру результата;
6. допустимость перехода состояния;
7. проверка flag, если указан в качестве proof.

После успешной обработки VLS обновляется системным компонентом.

### Response

```json
{
  "accepted": true,
  "vulnerability_id": "uuid",
  "status": "checked",
  "verdict": "confirmed"
}
```

### Ошибки

```text
VULNERABILITY_NOT_FOUND (если нужен)
NO_ACTIVE_SESSION
INVALID_VLS_TRANSITION
FLAG_NOT_CONFIRMED
```

# 9. `finish_check_session`

Завершает текущую check-session.

Метод не принимает `verdict`.

Результат проверки должен быть предварительно зафиксирован через `submit_check_result`.

### Request

```json
{}
```

### Response

```json
{
  "session_id": "uuid",
  "state": "finished"
}
```

До завершения `sandboxd` проверяет наличие валидного результата.

Если результат не зафиксирован:

```text
RESULT_NOT_SUBMITTED
```

После успешного завершения последующие `check`-логи ссылаются уже на новый context.

==Аналогично с `start_check_session`, ожидается, что пентест-система не завершит сессию без разрешения `sandboxd`==

# 10. Agent Logging API

Все методы логирования являются append-only: они не изменяют уже записанные события.

## 10.1. `log`

Универсальный метод отправки агентского события.

### Request

```json
{
  "level": "info",
  "event": "tool_call",
  "message": "Running sqlmap against /api/login",
  "metadata": {
    "tool": "sqlmap"
  }
}
```

### Возможные `level`

```text
model – рассуждения, респонсы модели(контекст)
debug - дебаг лог, несущий доп нагрузку(результаты запроса и тп)
info – инфо о событии(старт/финиш тулкола)
warning – ворнинг
error – еррор
```

### Context

По умолчанию определяется `sandboxd`.

При необходимости пентест-система может явно указать:

```json
{
  "context": "global"
}
```

Допустимые явные значения:

```text
global
permanent (при наличии)
```

`check` вручную указывать не требуется: он определяется активной check-session.

## 10.2. Tool Logging

Для удобства downstream-обработки рекомендуется использовать специализированные event types.

Например:

```text
tool_start (info)
tool_result (debug)
tool_finished (info)
tool_error (error)
```

### `tool_start`

```json
{
  "level": "info",
  "event": "tool_start",
  "message": "Starting sqlmap",
  "metadata": {
    "tool": "sqlmap"
  }
}
```

### `tool_result`

```json
{
  "level": "debug",
  "event": "tool_result",
  "message": "sqlmap finished",
  "metadata": {
    "tool": "sqlmap",
    "result": "...",
    "exit_code": 0
  }
}
```

Конкретная структура `metadata` зависит от инструмента и не должна ограничиваться API.
Поле result несет в себе респонс, полученный инструментом, если таковой имеется(например, результат сетевого запроса к таргету)

==все зависит от реализации тулзов, но мне очевидно было бы удобно работать с чем то более-менее уницифицированым==

Можно рассматривать такой вариант:

Ответы target/application/tooling могут логироваться тем же API:

```json
{
  "level": "debug",
  "event": "target_response",
  "message": "...",
  "metadata": {
    "status_code": 200
  }
}
```

При этом большие бинарные или иные тяжёлые данные не обязаны передаваться через logging API.

Лог должен содержать метаданные либо ссылку/идентификатор внешнего артефакта, если такой механизм будет добавлен. (я бы не хотел с эти иметь дело, но как будто и не придется)
